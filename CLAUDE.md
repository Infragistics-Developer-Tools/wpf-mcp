# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A stdio MCP server exposing 9 read-only tools over Infragistics Ultimate UI for WPF: component registry, API reference, keyword search, docs search, project scaffolding, and theming. It has two runtimes over one data set: C# in `server/` (NuGet `Infragistics.Wpf.Mcp`, a `net10.0` `dotnet tool`, the only published package) and TypeScript in `src/` (npm packaging kept but no longer published). All data is pre-generated at build time into `src/data/` (gitignored) and served from `dist/data/` / the tool's `data/` folder as plain JSON/XAML file reads — no reflection or network at runtime. The TS server is frozen — don't edit `src/` — so new tools and behavior go into C# only and the two runtimes' output may differ (e.g. `get_wpf_api_reference` compaction and its `member` filter are C#-only). There is no parity contract or test any more.

## Commands

```bash
npm install
npm run build:all        # build:data + build: NuGet restore → C# type extractor → build-api → build-docs → build-themes → build-info → tsc
npm run build            # tsc only + copy src/data → dist/data. FAILS if src/data/ doesn't exist yet
npm run dev              # tsx src/index.ts (also needs src/data/ populated)
npm test                 # smoke test: drives dist/index.js over stdio, calls every tool (scripts/smoke-test.ts)
npm run build:dotnet     # dotnet build server/ (needs src/data/); npm run test:dotnet = smoke test against it
npm run pack:dotnet      # dotnet pack → nupkg/ (version from package.json; -- --version X.Y.Z overrides)
npm run typecheck        # tsc --noEmit for src/ and scripts/ — needs no data
npm run validate:package # pre-publish gate: data thresholds, nupkg contents (when nupkg/ exists), version consistency (-- --expected-version X.Y.Z)
npm run inspector        # MCP Inspector against dist/index.js
node dist/index.js --debug   # logs every tool call to $TMP/wpf-mcp.log (override: WPF_MCP_LOG)
```

Partial regeneration (each step validates its own output and aborts loudly on empty/missing input):

```bash
npm run build:data       # all of the below in order
npm run generate         # docs:restore + scripts/generate.ts (skips the C# extractor if type-info.json is fresh; --force) + build-api.ts
npm run generate:types   # C# reflection extractor only → nuget/type-info.json (gitignored)
npm run build:docs       # scripts/build-docs.ts → src/data/{docs-index.json,docs/}
npm run build:themes     # scripts/build-themes.ts → src/data/{theme-index.json,theme-resources/}
npm run build:info       # scripts/build-info.ts → src/data/build-info.json (Infragistics version, submodule SHAs)
npm run ensure-submodules
npm run docs:update      # pull latest for the 3 docs/theme submodules
```

Requirements: Node ≥ 20 and the .NET 10 SDK (pinned by `global.json`). The type extractor targets `net10.0-windows` with `UseWPF`, so `generate:types` only runs on Windows. Submodules `docs/docs-wpf`, `docs/docs-common`, `docs/wpf-resources` are auto-initialized by `build:docs`/`build:themes` via `scripts/ensure-submodules.ts`.

There is no unit-test suite or linter; `npm test`/`test:dotnet` are the stdio smoke tests (checks of C#-only behavior sit under `IS_DOTNET` in `scripts/smoke-test.ts`), and `npm run validate:package` the data + nupkg gate. All run in CI and before publish.

Release/publish process (`npm run release -- <bump>` → PR → GitHub Release with bare tag → `nuget-publish.yml` builds, signs and publishes the NuGet package, then lists non-prerelease versions in the MCP Registry), CI/cache layout, SHA-pinned actions, nuget.org trusted publishing, and data-source bumps are documented in `DEVELOPMENT.md` — read it before touching `.github/`, `server.json`, `server/*.csproj`, `scripts/version.ts` or `scripts/validate-package.ts`.

## Architecture

### Data pipeline (build time, `scripts/`)

- `nuget/WpfDocs.csproj` pins the Infragistics Trial package version (currently 26.1.21) and is the single place to bump it. `docs:restore` fills `nuget/packages/`.
- `scripts/type-extractor/Program.cs` loads every Infragistics DLL into one `AssemblyLoadContext` and writes `nuget/type-info.json` — a flat map of `"Assembly|Ns.Type.Prop" → {typeName,isNullable,isEnum,enumValues}` (public and protected, instance and static properties, plus static `ResourceKey`/`RoutedCommand` fields marked `isField`; keyed by full name because same-named types overwrote each other's entries), `"__baseTypes"` (`"Assembly|Ns.Type" → "Assembly|Ns.Base"`, generic bases as their definition), `"__xaml"` (`"Assembly|Ns.Type" → {xmlns, prefix, ns, xamlName?}`), `"__nonPublicTypes"` (internal / private nested types reflection positively sees as non-public; a type that can't be loaded is never listed), `"__nonPublicMembers"` (`"Assembly|Ns.Type.Member"` for members of public types that are internal / private / private protected — only when no member of that name on that type is public or protected), `"__members"` (`"Assembly|<XML doc ID>"` → `{sig?, params?, overrides?, obsolete?, hidden?, protected?}`: every public / protected method and constructor with its C# signature and parameter names — and, for an override of a generic base type's method, the doc ID tail of the method it overrides (`InsertItem(System.Int32,`0)` for `InsertItem(System.Int32,Ns.Column)`) — plus indexers, protected properties and events (`protected`: no public accessor; the XML docs list them like public ones), and any member marked `[Obsolete]` (with its message) or `[EditorBrowsable(Never)]`; the doc IDs are generated from reflection in the XML docs' own format, so they join on `<member name="M:…">`), `"__nonPublicMethods"` (doc IDs of the internal / private methods and constructors of those types), `"__memberTypes"` (the types `__members` covers) and `"__enums"` (`"Assembly|Ns.Type" → {flags?, values: [{name, value}]}`: every public enum, nested ones too, its values in declaration order with their numbers; `flags` for `[Flags]`) and `"__themeMappings"` (`"<Theme>" → {"Ns.Type" → "<Theme>.xamDataPresenter.xaml"}`: the controls each `Infragistics.WPF.Themes.<Theme>` DLL's ThemeManager theme styles and with which of its files — the theme's protected `Mappings`, filled by `ThemeBase`'s private `Initialize()`; keys that are no type, such as `Infragistics.Themes.MsControls`, are left out). The xmlns comes from System.Xaml's `XamlSchemaContext` over the DLLs' own `XmlnsDefinition`/`XmlnsPrefix` attributes — the most specific xmlns that resolves to exactly that type and under which no other type of that name (public or not) lives in a covered namespace, else `clr-namespace:` syntax naming the assembly; nested types are `Outer+Inner`. This is the only source of property types, enum values, inheritance and xmlns; XML docs alone give just summaries.
- `scripts/build-api.ts` parses the NuGet `*.xml` doc files (split-based chunking, not regex-over-whole-file, to avoid backtracking on multi-MB inputs), merges `type-info.json` (its regex-parsed strings are JSON-unescaped: the extractor writes `` ` `` and `<` as ```/`<`), then `enrichWithInheritance()` walks the `__baseTypes` chains by assembly + full name (cycle-guarded) over every parsed type — including bases that lost their short name to a same-named type, so XamGrid's `Cell` subclasses still inherit from it — copying parent members onto children tagged with `declaredOn`. Static key/command fields are listed with the properties (`isField`). Protected properties and events get `isProtected` (from `__members`; inherited copies keep it). Enum pages get `values` (`{name, value, summary, obsolete?}` in `__enums` order, summaries from the XML's `F:` entries; values hidden from IntelliSense are left out, `[Obsolete]` ones kept with their message) and `isFlags`; values don't count in short-name contests and aren't in `search-index.json` (adding their names reshuffled the top 10 of about half the common queries). Types are filtered by `EXCLUDE_SUFFIXES`/`EXCLUDE_CONTAINS`/`EXCLUDE_PACKAGES`, and non-public types (the XML docs also document ~2,000 internal classes such as `ActivePaneManager`) are left out via `__nonPublicTypes` before short-name collisions are resolved, so a public type wins its name. Members are dropped when their summary is `"internal"`, when `__nonPublicMembers` lists them, when their doc name has `#` (explicit interface implementations), or when they're hidden from IntelliSense; a method or constructor overload `__nonPublicMethods` lists is dropped too, while one of a type in `__memberTypes` with neither entry (its generated doc ID didn't match) is kept by name and counts as unsigned in the signature gate. Methods, constructors (public, with parameters only) and indexers get `signature` from `__members` and, from the XML, `parameters` (the `<param>` descriptions whose name is one of the `params`); `[Obsolete]` members move to the page's `obsolete` list with their message (inherited like other members), so the server can answer a lookup with the replacement. A type hidden from IntelliSense (`XamSparklineView`) gets no page or registry entry but stays in `allTypes` as a base; an `[Obsolete]` type keeps its page with `obsoleteMessage`. Inherited methods are matched by overload (doc ID tail, or the `overrides` tail), not name, and a member a type re-declares `[Obsolete]` or hidden blocks every further base's version of it (`TemplateColumn` hides `Column.ValueConverter`). build-api fails if fewer than 95% of methods get a signature (the generated doc IDs stopped matching). `stripXml` turns `<see cref>`/`<seealso>`, `<paramref>`, `<typeparamref>` and `<see langword>` into the name they refer to and decodes entities. When two types share a short name, the higher `familyRank()` wins the file name, so the name means the control family Infragistics recommends: a type of a retired control (`RETIRED_ASSEMBLIES`: XamGrid and the xamInputs, whose docs carry retirement banners) ranks lowest, and a legacy `Infragistics.Windows.<Area>` type ranks below a newer copy of it in `Infragistics.Controls.<Area>` / `Infragistics.<Area>` (`XamComboEditor`, `ThemeManager`; the area must match, so XamPivotGrid's `FieldChooser` is not a newer XamDataGrid one). Between equal ranks the one with more documented members wins — counted as before the non-public member filter, so no name switches type. The contest is replayed after the scan, in discovery order. Each of the others gets its own page, built and enriched the same way, in `api/alternates/{lookup}.json`: `lookup` is its full name, plus `, Assembly` when two assemblies have that full name too (`Caret`), and is what `get_wpf_api_reference` takes to open it. Every type of the name lists the others in `alternates` (`lookup`, member count after inheritance, xmlns, first summary sentence, enum value names; the winner marked `isDefault`); the same class listed under a second package would only be a `sameType` note there, not a page. The alternates come last in `search-index.json`, with `f` (their lookup; the winner's entry has its full name), and a `namespaces.json` entry lists its alternates (the legacy XamComboEditor). Each type's `xamlNamespace`/`defaultPrefix` (and `xamlName` for nested types) come from `__xaml`; types it lacks (open generics, non-public types, DLLs left out of XAML resolution) fall back to `clr-namespace:`. `namespaces.json` is only `Xam*`-prefixed types. `TFM_PREF` and `byVersionDesc` pick one lib folder per package, and only XML docs with their DLL beside them are read (Infragistics.WPF.Spreadsheet.Charts.Trial also ships XamSpreadsheet's XML).
- `scripts/build-docs.ts` converts `.adoc` topics to `docs/{slug}.json` + `docs-index.json`. docs-common topics use `{PlaceholderName}` variables resolved from `docs-common/DocsConfig.xml` for the `wpf` product; only folders in `COMMON_FOLDERS` are taken from docs-common (not `data-grid`: the web/Blazor grid; not `win-web-chart`: WinForms/ASP.NET UltraChart; not `scheduler`: the Xamarin XamScheduler, which WPF doesn't have — its topics have no WPF content and matched `xamSchedule` searches by substring; `COMMON_NOT_WPF` also leaves out productivity-tools' Xamarin.Forms App Map, Toolbox and data grid configurator topics, which only `ifdef::xamarin[]` blocks link), each mapped to the DocsConfig variable naming its control, which a topic whose metadata names no control gets (all of shape-chart, most of financial-chart); an unresolved `{Placeholder}` counts as no control, and the folder's alias (`financial-chart`, `FinancialChart`) becomes that control. Nearly every `.adoc` starts with a UTF-8 byte-order mark, stripped on read. A topic with no metadata `name` takes its file name as slug and is kept only with a title: its `= Title`, or failing that its first heading when every other heading is deeper (`== Title` over `===` sections). `include::file.adoc[]` lines are replaced by that file, as Asciidoctor does (path relative to the including file, nested includes too, cycle-guarded); the sources give no include attributes, so one (`leveloffset`, `tag`, `lines`…) fails the build, as do more than 3 includes whose file is missing (each is logged). Included fragments with no metadata `name` and no title (`shared-crossfieldrecordfiltering`) are not topics, and a file that is only an include of another topic (`xamdatagrid-external-filtering-copy`) is left out as a duplicate; one that puts a title of its own over it (`xamdatapresenter-field-grouping`) drops the pasted title. A file other topics include that has a metadata `name` but no title (`configuring-template-field`, the xamDiagram summary charts) is written, so `get_wpf_doc` still opens it, but its index entry has nothing to search on. A docs-wpf file is left out when docs-common has a file of the same name (the docs site serves the shared one; docs-wpf's `bulletgraph.adoc` is only a title). A topic's slug is its metadata `name`; when several files claim one (seven are named `piechart-selection`), the file named after it keeps it, a copy with the same title and body (`home-page`) is left out, and the others take their own file names and, in docs-common, their folder's control (their metadata, `controlName` included, is the other file's); two topics left with one slug, case-insensitively, fail the build. Like a WPF build of the docs, it keeps only WPF's platform content, using the `wpf` product's `BuildFlags` (`xaml,wpf`, matched case-insensitively): `ifdef::…[]` blocks for other platforms, `pick:[platforms="text"]` wording for other platforms, and whole topics whose metadata `buildFlags` name only other platforms (`docx-*` flags are output formats) are dropped. The body is Markdown: `#` headings, code in ``` fences with its language; code blocks are set aside before the prose clean-up, which would otherwise delete `{Binding}`-style tokens. Each index entry carries `mentions` (Xam* names in the body, lowercased → count), which `search_wpf_docs`' `control` filter matches besides the topic's tags and title. `search_wpf_docs` lists a topic published for several controls once (same title but for a `(xamX)` suffix, or same opening words, and same text but for Xam* names: `xamdatagrid-X` and `xamdatapresenter-X` pasting one include), as the copy for `control`, naming the others.
- `scripts/build-themes.ts` copies `Themes/` (newer ThemeManager family) and `DefaultStyles/` (legacy embedded-BAML `Theme="..."` family) XAML from wpf-resources and records per-file `targetTypes` parsed from `TargetType=` declarations — this is what makes "is component X themeable" lookups content-aware rather than filename-based. A `Themes/` file also gets the controls its theme maps to it in `type-info.json`'s `__themeMappings`: the ThemeManager styles most legacy controls too (XamDataGrid, the xamEditors, XamTreeGrid, XamTabControl…), through files that only merge their legacy styles (`RoyalDark.xamDataPresenter.xaml` is `<igThemes:DataPresenterRoyalDark />`) and name no `TargetType`, so before, `setup_wpf_theme(component: "XamDataGrid")` offered only `Theme="..."`. The build fails when a mapped file or theme is missing from wpf-resources (the submodule and the theme packages out of step). `setup_wpf_theme` then lists such a control under both families and, when it has a `Theme` property, says to use `ApplicationTheme` for an app-wide theme.
- `scripts/build-guard.ts` `assertBuildStep()` is the fail-loud convention: any step whose output could be legitimately zero due to a missing upstream must assert instead of `console.warn`.

### Runtime (`src/`, frozen — not published, not edited; kept for reference and the TS smoke test)

- `src/index.ts` — bootstrap: loads `namespaces.json`, `search-index.json`, `docs-index.json`, `theme-index.json` into memory once, defines the `--debug` logger, sets the server `instructions` (the original of `server/ServerInstructions.cs`, which is now the canonical version), and registers each tool with `readOnlyHint/idempotentHint: true, openWorldHint: false`.
- `src/tools/constants.ts` — `TOOL_DESCRIPTIONS` (long, prompt-engineered; they cross-reference each other by tool name).
- `src/tools/schemas.ts` — zod input schemas; `.describe()` text is agent-facing guidance.
- `src/tools/handlers.ts` — one `create<Tool>Handler(deps, log)` factory per tool returning `async (input) => CallToolResult`. Every return path (including `isError: true`) calls `log(toolName, input, text, ms)`. Output is markdown text. Search tools use OR/ranked token matching (name hits weighted over member hits over summary hits).
- `src/lib/*-loader.ts` — on-demand reads of `dist/data/api/{Type}.json`, `docs/{slug}.json`, `theme-resources/**.xaml` with exact-then-case-insensitive lookup. All paths go through `resolveInside()` in `safe-path.ts` (containment check, no character allowlist, because generated names contain backticks/spaces/braces).
- `src/lib/types.ts` — runtime shapes. `SearchIndexEntry` uses single-letter keys (`n,s,a,p,m`) to keep the ~5MB index small.

### C# runtime (`server/`)

- `Program.cs` — same bootstrap as `src/index.ts` on the official `ModelContextProtocol` SDK: stderr-only logging, `--debug` file log, `ServerInstructions.cs` (the server instructions; started as a copy of the TS ones), `.WithTools<T>()` per tool class.
- `Data/Models.cs` (records + `WpfJsonContext` source-gen), `Data/DataStore.cs` (startup indexes, on-demand loaders — `LoadApiType` takes a short name or a full name, which it resolves through the short name's page and its `alternates` — and the `ResolveInside` containment check), `Data/NameComparer.cs` (deterministic stand-in for JS `localeCompare`).
- `Tools/ComponentTools.cs`, `SearchTools.cs`, `DocsTools.cs`, `ThemeTools.cs` — one `[McpServerTool]` method per tool; parameter `[Description]`s are the agent-facing input guidance (originally ported from the zod `.describe()` text), DataAnnotations are schema-only constraints (the SDK doesn't enforce them; clamp/validate in code). `Tools/ToolDescriptions.cs` the tool descriptions (ported from `constants.ts`), `Tools/Enums.cs` the enum inputs, `Tools/ToolLog.cs` the `--debug` logger.
- `Infragistics.Wpf.Mcp.csproj` — `PackAsTool` + `PackageType McpServer`; `src/data/**` is a `Content` item with `Pack="false"` (it ships inside the tool folder, not as NuGet content), root `server.json` is packed as `.mcp/server.json`.
- Some JS quirks were ported on purpose (JS `""` falsiness for optional strings) — see comments at each site; keep them unless you mean to change agent-visible behavior.
- `server/**/*.cs` must stay LF (`.gitattributes` enforces it): raw string literals carry the file's line endings into descriptions/instructions, so a CRLF checkout would change the agent-facing text.

### Conventions worth knowing

- ESM with `module: Node16` — relative imports must use `.js` extensions even for `.ts` sources.
- `ApiEntry`, `DocIndexEntry`/`DocEntry`, and `ThemeIndex` shapes exist three times: `scripts/*.ts` (producer), `src/lib/types.ts` (Node consumer) and `server/Data/Models.cs` (C# consumer; scripts intentionally don't import from `src/`). Change the producer and `Models.cs` together. `src/lib/types.ts` is the one exception to "don't edit `src/`": additive fields need nothing there, but a breaking shape change must keep the TS server able to read the data, because CI still runs the TS smoke test against it.
- Adding or changing a tool is C#-only: `server/Tools/ToolDescriptions.cs` (description), the `[McpServerTool]` method in `server/Tools/` (+ `.WithTools<T>()` in `Program.cs` for a new class), and a case in `scripts/smoke-test.ts` under `IS_DOTNET` (the TS smoke test still runs in CI against the frozen TS server).
- `nuget/type-info.json`, `nuget/packages/`, `nuget/bin|obj/`, `src/data/`, `dist/`, `server/bin|obj/` and `nupkg/` are all gitignored build outputs — never commit them. The publish workflow regenerates them; what pins a release's content is `nuget/WpfDocs.csproj` + the submodule commits.
- `package.json` version and `server.json` version(s) must match — `scripts/version.ts` keeps them in sync; don't edit either by hand. The csproj has no real version (`0.0.0-dev`); `pack:dotnet`/CI inject it.
